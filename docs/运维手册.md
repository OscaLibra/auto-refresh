# 运维手册

> 面向 IT / 技术支持。开发侧的规范见 README 与 AR-SPEC-002。

## 一、日志位置

| 组件 | 位置 | 说明 |
| --- | --- | --- |
| content script | 目标页 F12 → Console，上下文切到扩展名 | 默认上下文是 `top`，不切看不到 `[AR]` 日志 |
| service worker | `chrome://extensions` → 本扩展 →「服务工作进程」 | 显示 `(inactive)` 是正常回收，点按钮唤醒 |
| 诊断流水 | 设置页 →「导出诊断到剪贴板」 | 最近 50 条事件，含原因码 |

`[AR]` 前缀 + 事件名。日常只需 `warn` / `error`；把设置页「输出调试日志」打开会出现 `info` 级（注册、启动、模式）。

**日志已脱敏**：打印的 URL 只保留 `origin + pathname`，query 与 hash 被去掉（可能含工单号 / token）。

## 二、诊断导出里看什么

导出的 JSON 有五段：`settings` / `rules` / `sessions` / `diag` / `userAgent`。

排查「从来不刷新」时按这个顺序看 `diag` 的最近几条：

| 事件 | 含义 | 下一步 |
| --- | --- | --- |
| `registered` | 该标签建立了会话，规则已生效 | 正常 |
| `no-match` | 当前 URL 没命中任何规则 | 让用户改规则（通常写得太具体） |
| `permission-missing` | 权限被撤销 | 设置页点「重新授权」 |
| `idle-timeout` | 到点，正在执行 | 正常 |
| `reload-blocked` | 被页面 `beforeunload` 拦了 | 建议该规则改用 ping |
| `ping-ok` / `ping-fallback` | 保活成功 / 失败降级 | 失败率高说明该站不支持 HEAD，调大阈值或改 reload |
| `patrol-reload` | content 失联，SW 兜底刷的 | 偶发正常；频繁说明页面被冻结/discard |
| `paused` | 用户暂停 | 正常 |
| `resync` | URL 变化或规则变更后重算 | 正常 |
| `clock-rollback` | 系统时间被改 | 偶发忽略 |

`sessions` 里每条会话是 `ar:session:{tabId}`，关注 `lastActivityAt`（最后一次活动）、`idleMs`（阈值）、`paused`、`lastExecResult`。

## 三、典型线上问题

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 从来不刷新 | 无匹配规则 / 权限被撤 / 全局关闭 / 规则停用 | 看 `diag` 是否有 `no-match` 或 `permission-missing` |
| 刷新太频繁 | 阈值过小；或开了「滚动算活动」但页面其实是自动滚动 | 调大阈值；关掉滚动计入 |
| 偶尔晚一分钟 | 后台标签定时器降频，属预期 | 不是 bug，别修 |
| 刷新后要重新登录 | 阈值 > 实测超时 | 用实测值调小 |
| 大面积失效 | 扩展更新后动态注册丢失（已由 `onInstalled` 重建，理论上不该发生） | 重载扩展触发重建；仍不行则回滚 |
| 某系统突然频繁弹确认框 | 该站新增 `beforeunload` | 该规则切 `ping` |
| 添加规则时报「脚本注册失败」 | 该站权限没给、或浏览器策略限制 | 点「重新授权」；仍失败导出诊断 |

## 四、版本升级与回滚

升级：替换整个目录 → `chrome://extensions` 点「重新加载」→ **所有已打开的目标页需要刷新一次**（旧 content 脚本会变成孤儿脚本，不会自动失效）。
`onInstalled` 会做一次幂等重建，补齐 `storage.local` 里规则对应的动态注册，用户无需重配。

回滚：保留上一版 zip 与版本号。手工安装场景需要重新分发；用 `ExtensionSettings` 策略下发时，把 `update_url` 指向旧版 XML 即可。

企业内分发建议（非本期范围，需额外实现 `managed_schema.json`）：

```json
{
  "ExtensionSettings": {
    "扩展ID": {
      "installation_mode": "force_installed",
      "update_url": "https://内网地址/updates.xml"
    }
  }
}
```

## 五、灰度

1. 第 1 天：3–5 名内部用户，其中**至少 1 名 iframe 架构系统的重度用户**、1 名长期把系统挂在后台的用户。
2. 观察 3 个工作日，收集三个数：误刷新次数、刷新被拦截次数、权限弹框次数。
3. 无阻断问题再全量。全量前把《使用手册》第一节「怎么临时关掉」发到群里。

## 六、日常维护节奏

- 每周看一次用户诊断反馈，先分类是**配置问题**还是**代码问题**（九成是配置）。
- 每月回归四条核心用例：TC-01（前台刷新）、TC-04（后台兜底）、TC-14（beforeunload）、TC-17（iframe）。
- 目标系统前端大版本升级后**不需要**回归本插件（不依赖任何 DOM 选择器），但要验证该站的 `beforeunload` 行为有没有变化。
- 发布前必跑：`node tools/verify.mjs`、`node tools/simulate.mjs`、`node tools/simulate-sw.mjs`。

## 七、发布前必查清单

- [ ] `manifest.json` 的 `version` 与 `package.json` 一致（verify 会校验）
- [ ] `permissions` 仍只有 `storage / alarms / scripting`，没有 `host_permissions`
- [ ] 没有残留 `console.log`（`debug` 分支除外）
- [ ] `settings.debug` 默认 `false`，默认阈值不是测试用的 1 分钟
- [ ] 三档图标齐全（16px 目视仍能认出是刷新图标）
- [ ] `CHANGELOG.md` 已更新
